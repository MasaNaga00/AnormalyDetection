# 本番前リハーサル手順書（マルチ信号トラック・遅延対応込み）

モデルデータで一連の流れを最後まで通し、**実データ投入時に自分が何をやるか**を
体で覚えるための手順書。所要 1〜2時間。

このリハーサルで確かめるのは次の4点。

1. 既存の合成データで従来どおり動くこと（パッチによる回帰がないこと）
2. 販社の報告遅れがある状態で、遅れて届いた月の異常が拾えること
3. 熟成カーブから `HORIZON_FIXED` / `C_REVISIT_MONTHS` を決める手順が回ること
4. 月次サイクル（run → レビュー → 台帳記入 → 翌月run → 消し込み）が回ること

## 1. 回帰確認 — 従来どおり動くか

まず遅延対応を切って、以前と同じ結果が出ることを確かめる。ここが合わないと
以降の差分が「パッチのせい」か「遅延のせい」か切り分けられない。

`settings.py` を一時的に編集：

```python
USE_HORIZON = False
```

```bash
python settings.py            # 設定一覧。use_horizon が False か確認
python test_suppress.py       # 検出器別抑制
python gen_sim_panel.py       # 合成データ生成
python run_month.py panel_初回.csv 台帳_空.xlsx
python run_month.py panel_翌月.csv 台帳_記入例.xlsx
```

**期待**：1回目 **7件**、2回目 **4件**。

> 引き継ぎ資料には「1回目 8件」とあるが、現在の `settings.py`
> （`BASE_THRESHOLD_PCT=5.0` / `B_MIN_OE=1.5` / `C_ALPHA=0.005`）で実測すると
> **7件**になった。2回目は4件で資料と一致し、消し込みの4項目もすべて一致した
> ので、パッチによる回帰ではなく当時の設定差と考えている。
> ご自身の環境でも7件なら想定どおり。8件になったら当時の設定が残っている。

- 合わない → パッチの問題。ここで止めて、差分を持って相談する
- `test_suppress.py` が落ちる → `status()` の `event_ym` 追加が影響した可能性

`USE_HORIZON = False` は遅延対応前と**完全に同一挙動**になるよう作ってある
（`verify_lag.py` で差0確認済み）。ここで合えば土台は無事。

```bash
python verify_lag.py    # 遅延対応そのものの単体検証。4項目すべて通ること
```

### ★ 確認できたら `USE_HORIZON = True` に必ず戻す

**ここを戻し忘れると Step 5 以降が成立しません。** `USE_HORIZON` はマスタスイッチで、
`False` のあいだは horizon だけでなく **`C_REVISIT_MONTHS` も無効**になり、
信号Cは最新月の1ヶ月しか判定しません（＝遅れて届いた過去月が一切出ない）。

戻し忘れは `run_month.py` と `diagnose_signal_c.py` が警告を出すようにしてあるので、
実行時の冒頭を必ず読むこと。

```
[注意] USE_HORIZON=False です。horizon も C_REVISIT_MONTHS も無効で、
       信号Cは最新月の1ヶ月しか判定しません（遅れて届いた過去月は出ません）。
```

## 3. 熟成カーブを読み、horizon を決める

**これが実データでも最初にやる作業。** 本番の判断が一番大きいのがここ。

```python
import pandas as pd, panel_maturity as pm, settings as st
raw = pd.read_csv("遅延_run2.csv", encoding="utf-8-sig")
dist = raw[raw[st.COLS["dist"]] != st.ALL_TOKEN]
print(pm.explain(dist, st.COLS, target=0.95, max_lag=8).to_string(index=False))
```

### 見るところ

**① ρ(k) が単調に1へ近づいているか。** これが最重要。

```
販社  k0    k1    k2    k3    k4    k5
 A  0.85  1.00  1.02  0.99  1.01  1.00     ← 良い形
 D  0.00  0.00  0.41  0.76  0.94  0.99     ← 良い形（遅いが単調）
 X  0.62  1.31  0.44  1.18  0.87  1.03     ← 読めない。推定が効いていない
```

ガタガタなら、その販社は推定を諦めて `max_lag` で切る（保守側）。
判断できないときに深く切るのは安全。落とした月は再評価窓で拾い直される。

**② 推奨 `C_REVISIT_MONTHS`。** これが `settings.py` に入れる値。

**③ 遅れ月数の最大値。** これより `C_REVISIT_MONTHS` が小さいと、
その販社の月は**一度も検定されない**。`run_month.py` が警告を出すが、
ここで先に気づけるとよい。

### settings.py に反映

```python
USE_HORIZON = True
C_REVISIT_MONTHS = 6        # explain() の推奨値
HORIZON_FIXED = {}          # 推定に任せるなら空。読めない販社だけ手で入れる
```

`HORIZON_FIXED` を空にすると `reporting_horizon` の自動判定（末尾の痩せ具合）が
効く。これは熟成カーブより粗い推定なので、**explain() の結果と食い違うなら
explain() 側を信じて `HORIZON_FIXED` に手で書く**。

```python
HORIZON_FIXED = {"C": 202504, "D": 202503}
```

> 判断に迷ったら深めに切る。浅く切る誤り（未確定月を判定に入れる）は
> 誤報方向で危険、深く切る誤りは再評価窓で拾い直されるだけ。非対称。

## 4. 操作点を実測する

**必ず Step 3 の後。** 判定行数が再評価窓の分だけ増えるので、順番が逆だと
やり直しになる。

```bash
python tune_c_alpha.py 遅延_run2.csv
python tune_b_minoe.py 遅延_run2.csv
```

### 信号C（`C_ALPHA` / `C_MIN_COUNT`）

見るのは **`単位月最大`**（機種×部番に畳んだ件数の最大月）。平均3件でも
最大20件の月があれば、その月は破綻する。同じ部品で複数販社が同時に鳴るので、
`月平均`（販社別の行数）より実態に近い。

**スイープの値は定常状態の下限。** 実運用では次の2つが上乗せされる。

1. 初回runは `C_REVISIT_MONTHS + 1` ヶ月ぶんがまとめて出る
2. 上位N件に入らず台帳に記録されなかった月は、翌月も再登場する（再競争の設計どおり）

**件数を減らしたいときは `C_MIN_COUNT` を先に試す。** 信号Cの注目度は
`log(p)/log(alpha)` なので、`C_ALPHA` を絞ると生き残った行のスコアも一律に
下がり、統合ランキングで閾値・信号Bより下に沈む。`C_MIN_COUNT` には
この副作用がない。

`step1_scan` は `settings.USE_HORIZON` に従って horizon を適用する。
horizon と遅れ月数が最初に表示されるので、`C_REVISIT_MONTHS` が足りているかを
ここで確認できる。

### 信号B（`B_MIN_OE`）

まず判定対象の内訳が出る。

```
機種×SF の組合せ: 78 → require_full(cover>=36): 60 → min_peers>=2: 59 = 判定対象
  require_full で落ちた機種: ['M11', 'M12', 'M13']（窓を完走していない若い機種）
```

**どこで母数が減ったかを見る。** `require_full` で落ちるのは若い機種なので、
`B_ELAPSED_CAP` を短くすれば増える（が比較期間は短くなる）。実データで
`B_ELAPSED_CAP` を決めるときに直接必要な情報。

次に O/E の分布。**`B_ALPHA` は触らない**（効かない）。主レバーは `B_MIN_OE`。

初回は `B_MIN_OE = 2.0` にしておく。信号Bは発火すると12ヶ月抑制されるので、
制約は月次の定常件数ではなく初回の総件数。上澄みから着手して、落ち着いてから下げる。

**分布だけで決めず、必ず3つを叩く。**

```python
import pandas as pd, tune_b_minoe as tb
s = pd.read_csv("scan_b.csv", encoding="utf-8-sig")

tb.top_list(s, min_oe=2.0, alpha=0.005)      # ① 境界に何が来るかを目視
tb.top_list(s, min_oe=1.2, alpha=0.005)      #    一段緩めると何が増えるか
tb.confirm("遅延_run2.csv", min_oe=2.0, alpha=0.005)   # ② 本番(2パス)で確認
tb.nb_profile("遅延_run2.csv")                # ③ 沈黙する群の特定
```

**① `top_list` が一番効く。** 「これは異常」「これは機種特性」と人が判断できる
境界がO/Eのどこにあるかは、実データなら見れば分かる。統計量より信頼できる。
`tune_b_minoe.py` を実行しただけでは呼ばれないので、上のように明示的に叩く。

**② `confirm` を飛ばさない。** `scan()` は1パス（`two_pass=False`）で計算している。
2パス目の「発火機種をピアプールから外す」判定は min_oe/alpha に依存するので、
1回のスキャンで全操作点を表せないためで、これは意図的な設計。

その結果、**scan_b.csv の O/E 分布は本番より低く出る**。リハーサルデータでの実測:

| | O/E中央 | P90 | P95 |
|---|---|---|---|
| scan_b.csv（1パス） | 0.95 | 1.11 | 1.20 |
| 本番（2パス） | **1.01** | 1.12 | 1.20 |

異常機種をピアプールから外すと正常機種の O/E が1.0へ是正されるため。
今回は min_oe=2.0 なので発火件数は変わらないが、min_oe を 1.3〜1.5 に置くなら
この差が効く。**同一SF群に複数の異常があると、本番の方が多く発火する。**

**③ `nb_profile` で構造的な穴を見ておく。**

```
=== ピア不足で沈黙する (SF, nb) : 1件 ===
biz     sf  nb  同nb機種数
 E1 SF-104   3       1
```

SF-104 で nb=3 の機種が1つしかないので、`min_peers=2` を満たすピアが0。
これが X5（M04、3.0倍の異常）が判定対象から外れる理由。**実データの
幅≥1の群（約85群）で同じことが起こる構造的な穴**なので、
どのSF群がこれに当たるかを先に把握しておく。

### レビュー（ここが本番と同じ作業）

`出力/YYYYMM/レビュー用_YYYYMM.csv` を開く。上位15行が対象。

新しく増えた列の読み方：

| 列 | 意味 |
|---|---|
| `判定年月` | 台帳に書く年月。**最も古い発火月**が入る |
| `対象月内訳` | 実際に発火した月の一覧。`202503/202506` なら2ヶ月ぶん |
| `遅延月` | 判定年月が run年月から何ヶ月前か。>0 なら報告遅れで今回はじめて出た |
| `run年月` | 実行した月 |

`遅延月 > 0` の行は「3ヶ月前に起きていたが今まで見えていなかった」もの。
**現在進行形の異常とは緊急度が違う**ので、レビュー時に区別する。

処置区分を8択から選んで記入し、台帳（`台帳_L記入.xlsx`）に追記する。
リハーサルなので中身は適当でよいが、**次の3つは必ず1件ずつ作る**。

- `対策中`（再評価年月を数ヶ月先に）… 2回目で消えることを確認する
- `保留` … 2回目でも出続けることを確認する
- `新常態受容`（上書き閾値を現在の観測率+0.5に）… 2回目で消えることを確認する

そして **`検出器` 列を必ず埋める。** 空欄だと「全検出器」扱いになり抑制の
効き方が変わる。半年後のCUSUM評価の土台でもある。

**`判定年月` は必ずレビュー用CSVの値をそのまま写す。** run年月に書き換えると、
次回runで同じ過去月が再判定されたときに抑制が効かず二重に出る。

3. あって `alert_dist=True` なのにインボックスに無い → 台帳の抑制か top_n

## 8. 本番移行チェックリスト

## 9. 運用ガイドに書いておく既知の穴

現場が「バグだ」と受け取らないよう、先に明記しておく。

| 現象 | 性質 |
|---|---|
| nb混在群の機種が信号Bで沈黙 | 構造的。nb層別でピアが足りない。閾値側で拾う |
| 同SF群の全機種が不良だと信号Bが沈黙 | 横断比較の原理的限界。時系列側でしか拾えない |
| 緩やかな上昇トレンドで信号Cが鳴る | ローリングベースラインが遅れて追随するため。単月か継続かを目視で切り分ける |
| 累積使用率が実際より低く出る | 報告遅れで分子だけ欠ける。見逃し方向のみ。翌月自動是正 |
| 経過月が小さい部品が上位15件に入りにくい | 検知はできているが順位で沈む。経過月の小さい行を別途目視 |
| 遅れて届いた月の異常が数ヶ月後に出る | 仕様。`遅延月` 列で区別する |

## 10. 毎月やること（定着後）

```bash
python run_month.py panel.csv 台帳.xlsx
```

1. 受領状況を見る（`再評価窓不足` が出ていないか）
2. レビュー用CSVの上位15件をレビュー。`遅延月 > 0` は緊急度を区別
3. 台帳に処置区分を追記。**`検出器` 列を必ず埋める**
4. 台帳を日付つきでバックアップ
5. `統合インボックス_YYYYMM.csv` を Tableau で更新（Ctrl+Alt+F5）

スナップショットは `run_month.py` が自動で保存する。

半年ごと：`panel_maturity.build_triangle()` で熟成カーブを較正し、
`HORIZON_FIXED` / `C_REVISIT_MONTHS` を実測値に更新する。

### A-4. `判定年月` の罠（Step 5 の注意が実測で裏づけられた）

同じ2回目のrunを2種類の台帳で実行した。

| 台帳の `判定年月` | 結果 |
|---|---|
| `202503`（レビュー用CSVのまま） | 9→8件。信号Cが正しく消えた |
| `202506`（run年月に書き換え） | 9件のまま。**同じ行がもう一度出た** |

抑制は「判定年月 ≤ 発火月 < 再評価年月」で判定するため、判定年月を後ろに
ずらすと発火月をカバーできなくなる。**レビュー用CSVの値をそのまま写すこと。**

### A-5. 覚えておくべき挙動：再評価窓は「遅れが無くても」過去月を出す

`USE_HORIZON=True` にすると、報告遅れが一切ない合成データでも
過去月の信号Cが出た（上の例では2件）。

これは不具合ではない。`C_REVISIT_MONTHS=6` は「直近6ヶ月を毎回判定し直す」
という意味なので、**これまで一度も検定していなかった月の答え合わせ**が
初回にまとめて出る。2回目以降は、台帳に記録済みの月が抑制で消える。

ただし2つ、運用上の含意がある。

- **`C_ALPHA` の実測は再評価窓を入れた状態で行う。** 判定行数が (K+1) 倍近くに
  増えるので、窓なしで測った値では件数が合わない（Step 4 の順序の根拠）。
- **上位N件に入らなかった過去月の発火は、記録されないので翌月も出る。**
  これは「本物はSが伸びて翌月上位に来る」という再競争の設計思想どおりだが、
  K ヶ月ぶん居座るということでもある。件数が問題になるようなら、
  スナップショットの前回カバレッジと突き合わせて
  「前回のrunでは見えなかった月」だけに絞る改良が可能（未実装）。
