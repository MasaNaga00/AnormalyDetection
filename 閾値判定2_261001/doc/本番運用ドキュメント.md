## 1-2. パネルの投入前チェック

```bash
python check_panel.py panel.csv
```

**渡すデータを事前に加工する必要はない。** 年月の変換と累積販売台数の
`cummax` 補正は、`run_month.py` / `tune_c_alpha.py` / `tune_b_minoe.py` が
すべて同じ前処理として自動で通す。補正済みのデータを渡しても
（cummax は冪等なので）害はないが、補正した行数が見えなくなる分だけ損。

`check_panel.py` が8項目を見る。**自動で直るもの／直らないもの**を切り分ける。

| 項目 | 自動で直る？ |
|---|---|
| 年月のハイフン区切り | ○ 数字抽出で変換 |
| 年月の桁数ばらつき（`2023-2`） | ✗ **元データ側で直す。5桁は別の年月に化ける** |
| キーの重複 | ✗ **合算されない。露出も件数も二重になる** |
| 月次使用数の負値 | ✗ 下記 |
| 累積販売台数の非単調 | ○ cummax。ただし大きい逆転は要確認 |
| ALL行と販社別合計の不一致 | ✗ 要検討 |
| 経過月・SF-CODE の欠損 | ✗ その行は信号Bの対象外になる |

- [ ] `✗ 要対処` が無いこと
- [ ] `△ 確認` の内容を理解していること

### 月次使用数の負値（返品・訂正）

**これが一番やっかい。** 影響の向きが検出器で逆になる。

- **信号C** … ベースライン窓の合計が過小 → その後の月が過大に鳴る（**誤報方向**）
- **信号B・閾値** … 分子が過小 → 見逃し方向

対処は0クリップではない。0にすると累積が合わなくなる。
返品・訂正が原因なら**元の月に付け替える**のが正しい。それができない場合は、
`check_panel.py` が出す件数と大きさを見て、許容できる規模か判断する。

### 累積販売台数の逆転

`check_panel.py` が**相対幅**を出す。

- 数%以下の小さな逆転 → cummax 補正で問題なし（引き継ぎ資料の判断どおり）
- **相対幅が大きい／特定の販社や機種に集中** → 「本当に台数が減った」可能性
  （市場撤退・廃棄など）。この場合 cummax は分母を高止まりさせ、
  率を過小にする＝見逃し方向。元データの意味を確認すること

## 1-4. 熟成カーブ → horizon と再評価窓

```python
import pandas as pd, panel_maturity as pm, settings as st
raw = pd.read_csv("panel.csv", encoding="utf-8-sig")
dist = raw[raw[st.COLS["dist"]] != st.ALL_TOKEN]

pm.explain(dist, st.COLS, target=0.95, max_lag=8)        # ① カーブを読む
pm.suggest_settings(dist, st.COLS, target=0.95, max_lag=8)  # ② 貼る形で出す
```

### ① カーブの読み方

**見るのは左端だけ。** k=0,1,2 が低くて右へ上がっていれば打ち切りが見えている。

```
販社   k0    k1    k2    k3    k4    k5    k6   成熟域中央  成熟域の幅
 A  0.37  0.76  0.87  1.13  1.18  0.91  1.02      1.07    0.27   ← 読める
 N  2.00  1.00  2.50  1.25  1.67  1.00  1.67      1.46    0.67   ← 読めない
```

**成熟域（右側）が 0.5 や 2.0 に振れるのは打ち切りではない。**
そこはもう出そろっている領域なので、ρ は単に**月ごとの実変動**を測っている。
本当に修理が多かった月は 2、静かな月は 0.5 になる。異常ではない。

判断材料は `成熟域の幅`（右端4ヶ月の最大−最小）。

| 幅 | 意味 | 対処 |
|---|---|---|
| 〜0.3 | カーブが読める | 推奨値をそのまま使う |
| 0.3〜0.5 | やや荒い | 推奨値 +1 ヶ月くらい見ておく |
| 0.5〜 | **読めていない** | その販社は `max_lag` で保守的に切る |

幅が大きくなるのは、その販社の単位数が少なく月次件数が薄いときが典型。
`基準レート` が他販社より1桁小さければ薄い販社。

### ② 設定に落とす

`suggest_settings()` が貼れる形で出力する。

```
C_REVISIT_MONTHS = 3
HORIZON_MARGIN_OVERRIDES = {
    "A": 3,   # 最終月202503 → horizon 202412（Tから3ヶ月前）
    "N": 1,   # 最終月202503 → horizon 202502（Tから1ヶ月前）
}
```

**`HORIZON_MARGIN_OVERRIDES` を使う。`HORIZON_FIXED` は使わない。**

| | 単位 | 基準 | 毎月の更新 |
|---|---|---|---|
| `HORIZON_MARGIN_OVERRIDES` | **月数**（相対） | その販社自身の最終月 | **不要** |
| `HORIZON_FIXED` | **YYYYMM**（絶対） | — | **毎月必要** |

`HORIZON_FIXED` に `202412` と書くと、翌月も翌々月も 202412 のまま止まる。
**horizon が進まなくなり、新しい月が永久に評価されない。**
使うのは受領管理表の実測値を一時的に入れるときだけで、常用しない。

- [ ] `USE_HORIZON = True`
- [ ] `C_REVISIT_MONTHS` = 推奨値
- [ ] `HORIZON_MARGIN_OVERRIDES` = 貼り付け（読めない販社は max_lag 相当を手入力）
- [ ] `HORIZON_FIXED = {}` のまま

> `HORIZON_MARGIN_MONTHS` と `C_REVISIT_MONTHS` は逆向きに効く。
> margin は「末尾から捨てる月数」で 0〜1 が普通。遅れに対応するために
> 大きくするのは `C_REVISIT_MONTHS` のほう。


## ① 受領状況を見る（発火件数より先に）

```
=== 販社の報告遅れ（global horizon = YYYYMM）===
販社  最終年月  痩せ比  採用margin  horizon  遅れ月数  判定
```

- **`判定=再評価窓不足`** → `C_REVISIT_MONTHS` を上げる。放置するとその販社の月が永久に未検定
- **`採用margin` が 2以上** → 自動判定が暴れている。`HORIZON_MARGIN_OVERRIDES` で固定
- **`遅れ月数` が普段より大きい** → 販社側の運用が変わった可能性。確認する

受領状況そのものが業務情報になる。「D社が3ヶ月遅れている」は
検知以前に是正すべき事実。

## ② 上位15件をレビュー

`出力/YYYYMM/レビュー用_YYYYMM.csv`

**`遅延月` で降順ソートすると、報告遅れで今回はじめて判定できた行がまとまる。**
これらは過去の事象なので、現在進行形の異常とは緊急度が違う。区別して扱う。

判断のとき見るもの:

| 見るもの | 意味 |
|---|---|
| `検出器` | 複数そろっていれば真陽性率が高い |
| `統合注目度` | 並び順。3.0が各検出器の上限、+0.5×(検出器数-1) |
| `指標` | 各検出器の生の数字 |
| `対象月内訳` | 複数月にまたがっているか |
| `遅延月` | >0 なら過去の事象 |

**信号Bの沈黙は「正常」の証拠ではない。** `信号B詳細_YYYYMM.csv` に
その機種×SFの行が無ければ「監視できていない」であって「正常」ではない。
nb層別でピアが足りない群がこれに当たる（1-5 の `nb_profile` で把握済みのはず）。

## ③ 台帳に追記

レビュー用CSVの **A〜F列を台帳のB〜G列に貼る**（並びが一致している）。

| 台帳の列 | 記入 |
|---|---|
| A 記録日 | 手入力 |
| B〜G | レビュー用CSVから貼り付け |
| H 処置区分 | ドロップダウンから選択 |
| I 再評価年月 | 空欄なら検出器ごとの既定月数 |
| J 上書き閾値 | 新常態受容のときだけ。`提案Y下限` を写す |
| K〜O | 空欄（CUSUM専用） |
| P 原因メモ | `指標` を貼っておくと後で効く |
| Q 確認者 | 手入力 |

**厳守2点。**

- **`判定年月` は書き換えない。** run年月に直すと次回runで抑制が効かず二重に出る
- **`検出器` を必ず埋める。** 空欄は「全検出器」扱いになり、抑制が広がる

## 同じ月に複数回実行するとき

**検知結果には一切影響しない。** 状態を保存せず毎回パネル＋台帳から再生する
設計なので、何度回しても同じ入力なら同じ結果になる。

上書きされるものが3つある。

| 対象 | 挙動 |
|---|---|
| `出力/YYYYMM/` の各CSV | 上書き。レビュー済みの内容が変わりうる |
| `snap_YYYYMM.csv` | 上書き。旧版は `履歴/` に退避、`snapshot_log.csv` に追記 |
| 台帳 | 触らない（人が書くもの） |

**スナップショットの上書きは意図的。** 発展表の遅れ軸は「月」単位なので、
同じ月の複数時点を両方残すと、違う熟成度の観測が同じ遅れ k に混ざって
ρ(k) が歪む。最後の1本（＝最も出そろっている）だけを残すのが正しい。

**ただし試し実行では `--no-snapshot` を付ける。**

```bash
python run_month.py panel_一部.csv 台帳.xlsx --no-snapshot
```

切り出したパネルや検証用データで回すと、その月の正規のスナップショットが
痩せたデータで置き換わる。履歴に退避されるので復旧はできるが、
最初から汚さないほうがよい。

**レビュー中の再実行に注意。** レビュー用CSVを見ながら台帳を書いている途中で
再実行すると、CSVの中身が変わって行がずれる。**台帳を書き終えてから**
次を回すこと。判断の記録は台帳にしかない。

`snapshot_log.csv` は追記のみで上書きされない。行数や使用数計が普段と
大きく違う行があれば、そのとき異常なパネルで回した可能性がある。

# 運用ガイドに明記する既知の穴

現場が「バグだ」と受け取らないよう、先に共有しておく。

| 現象 | 性質 |
|---|---|
| nb混在群の機種が信号Bで沈黙 | 構造的。ピアが足りない。閾値側で拾う |
| 同SF群の全機種が不良だと信号Bが沈黙 | 横断比較の原理的限界。時系列側でしか拾えない |
| 緩やかな上昇トレンドで信号Cが鳴る | ローリングベースラインが遅れて追随。単月か継続かを目視で切り分け |

| 遅れて届いた月の異常が数ヶ月後に出る | 仕様。`遅延月` 列で区別する |
