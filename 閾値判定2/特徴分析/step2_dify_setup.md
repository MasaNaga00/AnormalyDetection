# Step 2-① 探索：Dify 設定と実行手順

`20261006_step2_explore.py` から呼び出す Dify ワークフローアプリを **2つ** 作ります。
どちらも「開始 → LLM → 終了」だけの最小構成です（JSON の整形・検証は Python 側で行います）。

---

## アプリ1：フレーズ抽出（環境変数 `DIFY_KEY_EXTRACT`）

### 開始ノード
| 変数名 | 型 | 備考 |
|---|---|---|
| `records` | 段落（paragraph） | 最大長を大きく（例 30000）。JSON 配列 `[{"id","text"}]` が入る |

### LLM ノード
- モデル：GPT-4o mini または GPT-4.1 mini
- temperature：0
- 最大トークン：4000 程度（8件 × 1件あたり約300トークン + 余裕）
- JSON モード（response_format: json_object）が選べれば ON

**SYSTEM**
```
あなたはカメラ・レンズの修理記録を読み解く品質保証の専門家です。
入力は修理記録の JSON 配列です。各記録の text には、お客様の申告と修理者のコメントが混在しています。
[お客様コメント] [修理者コメント] の欄名は当てになりません（お客様欄に修理者の所見が書かれていることがあります）。
内容から「誰の記述か」を判断してください。言語は英語・ドイツ語・フランス語・中国語・日本語などさまざまです。

各記録について、以下を日本語で抽出してください。
- symptom  : お客様が訴えている症状（例:「電源が入らない」「AFが合わない」「ズーム時異音」）
- situation: 発生時の状況・きっかけ（例:「落下後」「雨天使用後」「起動時」「長時間使用後」）
- finding  : 修理者が確認した所見・原因（例:「基板腐食」「フレキ断線」「ギア摩耗」「再現せず」）
- external : 外因（落下・水濡れ・砂・衝撃・改造・不適切な使用）の記載。"あり" / "なし" / "不明"
- summary  : 記録全体の日本語1行要約（40字以内）
- evidence : 判断の主な根拠となった原文の抜粋（原文のまま、60字以内）

規則:
1. symptom / situation / finding は、それぞれ最大3つの短いフレーズのリスト（各20字以内）。
   表現は「名詞句」または「〜しない」の簡潔な形にそろえる。
2. 書かれていないことは推測しない。該当する記述がなければ ["記載なし"]。
3. 作業内容（交換・調整・清掃・ファーム更新など）は所見ではない。所見が書かれていなければ finding は ["記載なし"]。
4. エラーコードはフレーズに含めてよい（例:「Err20表示」）。
5. 入力と同じ件数・同じ id で返す。id は入力の文字列をそのまま使う。
6. 出力は次の JSON のみ。説明文は書かない。

{"results":[{"id":"...","symptom":["..."],"situation":["..."],"finding":["..."],"external":"不明","summary":"...","evidence":"..."}]}
```

**USER**
```
{{#開始.records#}}
```
（変数の挿入は Dify の画面で `records` を選んでください）

### 終了ノード
| 出力変数名 | 値 |
|---|---|
| `result` | LLM ノードの text |

## アプリ2：カテゴリ案（環境変数 `DIFY_KEY_CATEGORY`）

### 開始ノード
| 変数名 | 型 | 備考 |
|---|---|---|
| `axis` | 短文 | 「症状」「状況」「所見」のいずれか |
| `phrases` | 段落 | 最大長 30000。1行に「フレーズ<TAB>件数」 |
| `existing` | 段落 | 既存カテゴリ（「カテゴリ: 定義」の行）。無ければ「（なし）」 |

### LLM ノード
- モデル：GPT-4.1 mini 以上を推奨（まとめ上げの質が効くため）／temperature 0／最大トークン 6000 程度

**SYSTEM**
```
あなたはカメラ・レンズの修理データを分類する品質保証の専門家です。
修理記録から抽出した、指定された軸（症状・状況・所見のいずれか）のフレーズと出現件数が与えられます。
これらを件数集計に使えるカテゴリにまとめてください。

規則:
1. カテゴリ数は 8〜15 個を目安にする。件数の多い現象は細かく、少ない現象はまとめる。
2. 既存カテゴリが与えられた場合は優先して使い、当てはまらないものだけ新設する（new: true）。
3. 各カテゴリに、判定基準として使える定義（1〜2文）を付ける。「〜を含む／〜は含まない」まで書くと良い。
4. 1つのフレーズは1つのカテゴリにだけ入れる。phrases には入力フレーズを一字一句そのまま書く。
5. どこにも入らない少数のフレーズは無理にまとめず unassigned に入れる。
6. 「記載なし」「その他」はカテゴリとして作らない（別途固定で扱う）。
7. 出力は次の JSON のみ。

{"categories":[{"name":"...","definition":"...","phrases":["..."],"new":true}],"unassigned":["..."]}
```

**USER**
```
軸: {{#開始.axis#}}

既存カテゴリ:
{{#開始.existing#}}

フレーズ<TAB>件数:
{{#開始.phrases#}}
```

### 終了ノード
| 出力変数名 | 値 |
|---|---|
| `result` | LLM ノードの text |

## 実行手順

1. スクリプト冒頭の設定を合わせる
   - `REPAIR_FILE`、`COLS`（修理ID・開発コード・修理日・国）、`COMMENT_COLS`（コメント列。何列でも可）
   - `DIFY_BASE_URL`（例 `https://<社内Dify>/v1`）、必要なら `CA_BUNDLE`
   - 既存の症状カテゴリを使う場合は `EXISTING_CAT_FILE`（列：軸・カテゴリ・定義、軸は「症状」）
2. API キーを環境変数に設定（Windows PowerShell の例）
   ```
   $env:DIFY_KEY_EXTRACT  = "app-xxxx"
   $env:DIFY_KEY_CATEGORY = "app-yyyy"
   ```
3. 実行
   ```
   python 20261006_step2_explore.py extract   # まず抽出だけ
   python 20261006_step2_explore.py propose   # 抽出結果を確認してからカテゴリ案
   ```
   - 抽出結果は `step2_out/extract_cache.jsonl` に1件ずつ保存されます。途中で止まっても再実行すれば続きから処理します。
   - やり直したいときは、このキャッシュファイルを削除してから実行します。

## 出力と確認ポイント

`step2_out/step2_explore.xlsx`
| シート | 見るところ |
|---|---|
| 抽出結果 | 原文と抽出結果を20件ほど読み比べる。推測で埋めていないか、お客様の申告と修理者の所見が逆になっていないか |
| フレーズ頻度 | 同じ意味の言い換えがどの程度ばらついているか |
| エラーコード(全件) | 正規表現での抽出（LLM は使わない）。`E20` と `ERR20` のような表記ゆれは目視で確認 |
| 読込ログ | 除外件数・失敗件数 |

`step2_out/カテゴリ辞書_案.xlsx`
| シート | 見るところ |
|---|---|
| 辞書 | カテゴリ名・定義を修正・統合・分割する → 確定版が Step 2-② の入力になる |
| 未分類フレーズ | 新しいカテゴリを立てるべきものがないか |

## 次（Step 2-②）
確定したカテゴリ辞書を使って全件（100〜2000件）を分類 → 件数集計・直近／過去比較・国やロットとのクロス集計。
分類の前に、50件程度で人の判断との一致率を確認します。
