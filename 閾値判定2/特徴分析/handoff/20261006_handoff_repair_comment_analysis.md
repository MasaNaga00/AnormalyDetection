# 引き継ぎ資料：修理データ特徴解析編（ロット・国・コメント）

2026-10-06 作成。出庫異常検知とは独立した新しいトラック。

---

## 1. 目的と位置づけ

異常検知で引っかかった「機種×交換部番」について、その部品を交換した修理データに**特徴的な傾向があるか**を調べ、詳細調査（深掘り）に進むべきかを判断できるようにする。

- 対象は「修理で交換された部品」だけ。**出庫データとは結び付けない**（ユーザー判断）
- 比較の考え方は「対象群だけを眺めるのではなく、**比較群より何が多いか**（lift）」
- 成果物のイメージは、検知1件ごとの「特徴カード」（Excel／Tableau用の縦持ち表）
- 狙い：月15件程度のレビューで「深掘りすべきか」「外因（落下・水濡れ）が中心で製品起因ではないか」を短時間で判断できること

## 2. 前提・制約

| 項目 | 内容 |
|---|---|
| データ | 社外持ち出し禁止。Python 処理はローカル（Windows・社内環境） |
| ライブラリ | numpy・pandas・openpyxl のみ（**scipy 禁止**）。HTTP は標準ライブラリ urllib |
| LLM | **修理コメントは社内 Dify に送ってよい**（確認済み）。**Dify API を Python から呼べる**（確認済み） |
| 出力 | Excel（Tableau で読める縦持ち） |
| 進め方 | 実装前に設計を確認する。短い実装。ダミーデータで検証してから渡す |

## 3. データ仕様

### 確認済み
- 修理データは**1修理＝1行**。ユーザーが「交換部番が一致した修理」だけを抜き出して渡す
- 1修理で複数の部品を交換した場合も**1行**（交換部番が1セルに複数入る）→ 同時交換部品の解析が可能
- コメントは「お客様」「修理者」の欄があるが、**販社によって欄の使い方が違い、お客様欄に修理者のコメントが書かれていることもある**（欄の区別は当てにならない）
- 言語は国によって異なり、記述の詳しさもばらつきが大きい
- 件数は機種×部品によって約100〜2000件
- シリアル → 製造年月：**別表に `SN type` 列（B/C）があり、開発コードで結合できる**
  - `C` → シリアル頭3桁が製造年月コード
  - `B` → シリアル頭2桁が製造年月コード
  - プレフィックスから**実際の製造年月までの対応ができているのは一部の機種だけ**

### 未確認（実データで要確認）
- 修理データ・SN type 表の実際の列名（スクリプトの `COLS` は仮の名前）
- 交換部番セル内の区切り文字（現状はカンマ・読点・セミコロン・スラッシュ・空白を想定）
- 「プレフィックス → 製造年月」対応表の形式（現状は列が 開発コード／プレフィックス／製造年月 の表を想定）
- シリアルが Excel で数値保存されて先頭の0が欠けていないか
- 既存の症状カテゴリ（修理データ検索システムのもの）の実物。Step 2 の出発点として使ってよいことは了承済み

## 4. 全体構成

```
Step 1  構造化データの特徴カード（コメント不使用）        ← 実装済み・ダミー検証済み
Step 2  コメント解析
  ① 探索：自由フレーズ抽出 → カテゴリ案 → 人が確定      ← 実装済み・模擬応答で検証済み（実 Dify 未実行）
  ② 分類：確定辞書で全件を分類（JSON）                    ← 未着手
  ③ 集計：件数・直近／過去比較・国×症状、ロット×所見      ← 未着手（Step 1 の compare() を流用予定）
```

ユーザーは「Step 1 は一応動いたとして」Step 2 に進んだ。Step 1 の実データでの結果（読込ログ）はまだ共有されていない。

## 5. Step 1：構造化データの特徴カード

ファイル：`20261006_repair_feature_card.py`

### 比較の方法
- 同じデータの中で「**直近期間**（既定は最新から6か月）」と「**過去期間**」を比べる（比較方法A）
- 比較方法B（同じ機種の全修理を比較群にする）はデータが取れれば後から差し替える前提。A だけだと、国・ロットの偏りが単に販売構成や生産数を反映しているだけ、という可能性を否定できない

### 出力シート
| シート | 内容 | 判定 |
|---|---|---|
| 概要 | 機種ごとの件数、★の付いた国・ロット・同時交換部品 | — |
| 国 | 国ごとの直近／過去の件数・割合・lift・片側 Fisher p・補正後 p | ★あり |
| 製造ロット | プレフィックスごと。経過時間を補正した期待割合との比較（下記） | ★あり（製造年月が分かるロットのみ） |
| 使用期間 | 使用期間（修理年月 − 製造年月）の区分ごとの分布と中央値 | **参考表示のみ** |
| 同時交換部品 | 対象部番以外に同じ修理で交換された部番 | ★あり |
| 国x製造ロット | 期間×国×プレフィックスの件数（Tableau のヒートマップ用） | — |
| 明細 | 1修理1行。プレフィックス・製造年月・使用期間・同時交換部品 | — |
| 読込ログ | 日付の解釈失敗、SN type 不明、使用期間が負の件数など | — |

### 統計手法
- 国・同時交換部品：2×2 表の片側 Fisher（超幾何分布を `math.lgamma` で計算）。lift は0件対策として 0.5 を加えて計算
- ★の条件：補正後 p < 0.05、直近件数 ≥ 3、lift > 1
- 多重比較：表の中で直近件数 ≥ 3 のカテゴリ数を使った Bonferroni 補正

### 重要な設計判断（経緯つき）
1. **製造ロットを単純な直近／過去で比べてはいけない**
   - 新しいロットほど直近に修理が集中するのは当然なので、異常のない機種でも★が多発した（ダミーで確認）
   - そこで、各ロットの製造年月から「直近期間に入るはずの割合 q」を求め、実際の直近件数と**二項検定**で比べる方式にした
   - q は機種全体の「使用期間ごとの故障の形」から計算する。形は「使用期間 a の故障件数 ÷ 使用期間 a を観測できたロット数」で求める（**観測期間で途切れる分の補正**）
   - 検定対象のロット自身は形の推定から外す（**leave-one-out**）
   - 補正前は無シグナルでの誤検出が40カード中8件、補正後は1件
   - 製造年月が分からないロットは件数のみ表示し、判定しない
2. **使用期間の直近／過去比較は判定に使わない**：発売から時間が経つほど長い使用期間の修理が自然に増えるため
3. 1修理の中で同じ部品は1回として数える。修理IDの重複は除外する

### 検証結果（ダミー）
- 埋め込んだ異常（国TH・ロット305・同時交換FPC-77）はすべて★で検出
- 無シグナル40カードでの★：国2、ロット1、同時交換0
- ダミー出力のサンプル：`20261006_feature_card_dummy_sample.xlsx`（ロット503の★は乱数による偶然の偏り）

### 既知の限界
- 国の偏りは、販売構成の時間変化と区別できない（比較方法B で改善）
- 製造年月の対応表がない機種は、ロットの判定ができない

## 6. Step 2：コメント解析の設計

### 方針（検討済み）
**「①分類の型を作る → ②全件を型に当てはめる → ③集計」の3段階。**
- LLM の自由要約だけでは、表現が揺れて件数を数えられない
- 最初から分類を決め打ちすると、想定外の現象を見落とす

### 頻出単語（ワードクラウド）を採用しなかった理由
ユーザーから質問があり、比較のうえ現方式が優位と説明済み。
- 言語ごとに件数が割れる（power／Strom／开机／電源）。比べるには翻訳が要る
- 否定（no corrosion found）や因果が消える
- 欄が当てにならないため、お客様の申告と修理者の所見を分けられない
- 定型文やありふれた単語が上位を占める。記述の多い販社に引っ張られる
- 修理ごとのカテゴリがないので、Step 1 のような件数比較・クロス集計ができない
- 日中の単語分けにライブラリ（MeCab など）が必要

現方式の「フレーズ頻度」シートは「正規化後のワードクラウド」に相当する。エラーコードは LLM を使わず正規表現で抽出している。原文の単語頻度は、必要になれば単一言語に絞った照合用として追加すればよい。

### 分類の軸
| 軸 | 内容 | 例 |
|---|---|---|
| 症状 | お客様の申告 | 電源が入らない、エラー表示、異音、画像不良 |
| 状況 | 発生時の状況・きっかけ | 落下後、水濡れ、高温、特定の操作中 |
| 所見 | 修理者の確認結果 | 腐食、異物、破損、摩耗、断線、再現せず |
| 外因 | あり／なし／不明 | — |
| 補助 | 日本語の1行要約、根拠となった原文の抜粋 | — |

### 実装上の決めごと
- コメント欄を「[欄名] 本文」の形でつなげて1テキストにし、**誰の記述かは内容から LLM に判断させる**
- 原文の言語のまま読ませ、日本語のラベルで出させる（翻訳の工程は挟まない）
- 各軸に「記載なし」「その他」を固定で用意する。「書かれていないことは推測しない」とプロンプトで指示
- 作業内容（交換・調整・清掃）は所見に含めない
- 件数を数えるため、②では各軸の主ラベルを1つにする予定（①の探索では最大3フレーズ）
- Python から Dify を呼ぶ。1回8件、ID を照合し、欠けた分は1件ずつ再送（最大3回）。結果は JSONL にキャッシュし、再実行すると続きから処理する（以前の Dify バッチで出力が空になった問題への対策）
- エラーコードは正規表現で全件から抽出（日本語に隣接していても拾えるよう `\b` は使わない）
- 信頼性の確認：②の前に、50件ほどで人の判断との一致率を確認する。同じ記録を2回分類して、ぶれないかも見る

## 7. Step 2-①（探索）の実装状況

ファイル：`20261006_step2_explore.py`、`20261006_step2_dify_setup.md`（Dify 側の設定とプロンプト全文）

- Dify アプリは2つ（どちらも 開始 → LLM → 終了 の最小構成。終了ノードの出力変数名は `result`）
  - 抽出アプリ：入力 `records`（JSON 配列）→ 症状／状況／所見のフレーズ、外因、要約、根拠
  - カテゴリ案アプリ：入力 `axis`／`phrases`（フレーズと件数）／`existing`（既存カテゴリ）→ 8〜15カテゴリ・定義・含まれるフレーズ・未分類
- API キーは環境変数 `DIFY_KEY_EXTRACT`／`DIFY_KEY_CATEGORY`
- 実行：`extract` → 抽出結果を確認 → `propose`
- サンプル：150件（直近・過去で半分ずつ）。コメントが5文字未満のものは除外
- 出力
  - `step2_out/step2_explore.xlsx`：抽出結果・フレーズ頻度・エラーコード(全件)・読込ログ
  - `step2_out/カテゴリ辞書_案.xlsx`：辞書（軸・カテゴリ・定義・新設/既存/固定・サンプル内件数）・未分類フレーズ
- 検証：模擬応答（失敗・ID 欠落・コードフェンス付き・壊れた出力を混在）で最後の出力まで通ること、再送で全件そろうこと、再実行で API を二重に呼ばないことを確認済み
- **実 Dify での実行とプロンプトの効き具合は未確認**

### ユーザー側の作業待ち
1. Dify にアプリを2つ作り、API キーを設定する
2. `COLS`／`COMMENT_COLS`／`DIFY_BASE_URL`（必要なら `CA_BUNDLE`）を実際の値に合わせる
3. 既存の症状カテゴリを Excel（列：軸・カテゴリ・定義）にして `EXISTING_CAT_FILE` に指定する
4. まず `extract` を実行し、「抽出結果」シートで原文20件ほどと読み比べる（推測で埋めていないか、申告と所見が逆になっていないか）

## 8. 次にやること

1. 実 Dify での `extract` の結果を見て、抽出プロンプトを調整する
2. `propose` → ユーザーがカテゴリ辞書を確定する
3. **Step 2-②**：確定辞書を入力にした分類用 Dify アプリと Python スクリプト（①のクライアント・キャッシュ・再送の仕組みを流用）。ラベルが辞書にない場合はエラーとして扱う。主ラベルは各軸1つ
4. 50件で人の判断との一致率を確認する
5. **Step 2-③**：カテゴリ件数、直近／過去の lift（Step 1 の `compare()` を流用）、国×症状・ロット×所見のクロス集計、「その他」の割合の監視（増えたら辞書を見直す）
6. Step 1 と Step 2 の結果を、検知1件ごとの特徴カードに統合する
7. （任意）比較方法B のデータが取れれば、比較群を差し替える
