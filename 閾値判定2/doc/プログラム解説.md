## 1. 全体像

```
                    panel.csv（機種×部番×販社×月）
                              │
                  run_month.py │ 投入前チェック（年月書式・cummax）
                              │ ALL行 / 販社別行 に分割
                              ▼
        ┌──────────── build_unified_inbox() ────────────┐
        │                                               │
        │  [0] 遅延レイヤー  reporting_horizon           │
        │        販社ごとの horizon を推定               │
        │                                               │
        │  [1] 閾値      state_logic.series_rates        │  ALL行
        │        累積使用率 ≥ 基準X(%) か                │
        │                                               │
        │  [2] 信号B     signal_b_peer.run_signal_b      │  ALL行
        │        同SF群のピア機種と比べて高いか           │  (horizonで打ち切り)
        │                                               │
        │  [3] 信号C     signal_c_dist.run_signal_c      │  販社別行
        │        直近12ヶ月と比べて当月が急増したか       │  (horizonで切る+再評価窓)
        │                                               │
        │  ── 各検出器が「候補行」を出す ──               │
        │                                               │
        │  [4] 台帳フィルタ  LedgerView.status()         │  台帳.xlsx
        │        終了・抑制・基準上書きを適用             │
        │                                               │
        │  [5] 統合      merge_candidates()              │
        │        1部品1行に畳んで統合注目度で並べる       │
        └───────────────────────────────────────────────┘
                              │
                              ▼
              出力/YYYYMM/ 各種CSV → 人がレビュー → 台帳に追記
```

**状態を保存しない設計。** 判定結果はどこにも永続化せず、毎回「パネル＋台帳」から
再生する。だから `asof_ym` を過去に振れば当時の判定を完全に再現できるし、
台帳を直せば過去にさかのぼって結果が変わる。これが監査再現性の根拠。

## 2. データ構造

### 2.1 パネル（入力）

1行 = 機種 × 部番 × 販社 × 年月。

| 列（`settings.COLS`） | 内部名 | 意味 |
|---|---|---|
| 事業コード 開発コード 部番 | biz dev part | 監視単位のキー |
| 販社 | dist | `ALL` = 全販社合計行。個別販社 = A〜E |
| 年月 | ym | YYYYMM。受付月（実イベント日） |
| 経過月 | elapsed | 発売からの月数。信号Bの窓に使う |
| 月次使用数 | use | 分子 |
| 累積販売台数 | fleet | 分母の素。**その月の保有台数** |
| SF-CODE | sf | 部品の種類。信号Bのピアキー |

**ALL行と販社別行は必ず分けて使う。** 混ぜると use も fleet も2倍になる。
`run_month.py` が `st.ALL_TOKEN` で分割している。

- 閾値・信号B → ALL行のみ
- 信号C → 販社別行のみ

**露出（E）は「台数×月」。** `fleet` を月方向に足し上げたもの。
1000台を12ヶ月見たら E=12000。件数 C をこれで割ればレートになる。

### 2.2 台帳（人間の判断・マスタ）

`unified_inbox.LEDGER_COLS` が読む列。Excel の他の列は無視される。

| 列 | 役割 |
|---|---|
| 事業コード 開発コード 部番 | どの部品の記録か |
| **検出器** | 閾値/信号B/信号C/CUSUM。複数なら `/` 区切り。**空欄は全検出器扱い** |
| **判定年月** | いつの発火に対する記録か。抑制の起点 |
| 処置区分 | 8択。これが振る舞いを決める |
| 再評価年月 | 抑制の終わり。空欄なら検出器ごとの既定月数 |
| 上書き閾値 | 新常態受容のときの新しい基準X(%) |
| 対象販社 | 信号Cで特定販社の話のとき（表示用） |

追記型。過去の行は消さない。`load_ledger()` が年月を YYYYMM に正規化する。

### 2.3 インボックス（出力）

1行 = 1部品。複数検出器が同じ部品を指したら1行にまとまる。

| 列 | 意味 |
|---|---|
| 検出器 | `閾値/信号C` のように連結 |
| 判定年月 | **台帳に写す値。最も古い発火月** |
| 対象月内訳 | 実際に発火した全月 |
| 遅延月 | run年月 − 判定年月。>0 なら報告遅れで今回はじめて出た |
| 統合注目度 | 並び順の物差し |
| 指標 | 各検出器の生の数字を人間向けに連結したもの |

## 4. 実行の流れ（`build_unified_inbox` を上から）

```python
# ① 遅延レイヤー（use_horizon=True のとき）
horizon   = rhz.estimate_horizon(panel_dist, ...)   # {販社: 完全な最終月}
hz_global = rhz.global_horizon(horizon)             # 全販社が揃う月 = min

# ② 閾値用の率テーブル
p_all = sl._prepare_panel(panel_all.rename(...))    # 列名を内部名へ + 月次0補完
rates = sl.series_rates(p_all, sl_cfg)              # 累積率テーブル
T     = rates["ym"].max()                           # 判定基準月
lv    = LedgerView(ledger, T, cfg)                  # 台帳を解決可能な形に

# ③ 信号B用のパネル（elapsed / sf が要るので CUSUM 側の前処理を使う）
p_b   = sc._prepare_panel(panel_all, sc_cfg)
p_b   = p_b[p_b["ym"] <= hz_global]                 # 全販社が揃う月で打ち切り
res_b = sb.run_signal_b(p_b, ...)

# ④ 信号C
res_c = sd.run_signal_c(panel_dist, cols, asof_ym=T,
                        horizon=horizon, revisit_months=K)

# ⑤ 候補を作って統合
cand  = [candidates_threshold(...), candidates_signal_b(...), candidates_signal_c(...)]
inbox = merge_candidates(cand, lv, cfg)
```

`T` は **ALL行パネルの最新月**。信号Cの horizon はこの T を基準に相対計算される。

## 5. 検出器ごとの中身

### 5.1 閾値 — `state_logic.series_rates` + `candidates_threshold`

一番単純。累積使用率が基準を超えたら発火。

```
累積使用率(%) = 100 × 累積使用数 / 累積販売台数
```

`series_rates` は販社別系列と「合算」系列の両方を作るが、**本線には ALL行しか
渡していない**ので、実質 `ALL` と `合算` の2系列が同じ値になる。
`candidates_threshold` は `rate_pct` が最大の系列を採るので、ここは実質 no-op。
販社別二次監視トラックを将来入れるときの余地として残っている。

```python
sub  = rates[(rates["ym"] == T) & rates["eligible"]]
thr  = st["thr_ov"] or sl.base_threshold(cfg, biz, dev, part)   # 上書き優先
pick = g.loc[g["rate_pct"].idxmax()]
if obs < thr: continue
生スコア = min(obs / thr, 3.0)
```

`base_threshold` は `(biz,dev,part)` → `(biz,dev)` → `(biz,)` の順に
`THRESHOLD_OVERRIDES` を探す。無ければ `BASE_THRESHOLD_PCT`。

**時間特性**：分母が積み上がるので単月の急増ではほとんど動かない。
確実だが遅い。ここを信号Cが補う。

### 5.2 信号B — `signal_b_peer.run_signal_b`

「同じ部品種類（SF）を持つ他機種と比べて、この機種だけ高いか」。

#### 集約（`build_peer_units`）

監視単位を **機種 × (biz, SF)** に畳む。部番は合算する。
これにより機種間で部番が違っても比較でき、部品対応表が不要になる。

```python
d = panel[panel["elapsed"] <= elapsed_cap]         # 経過月を揃える（発売年次の差を消す）

# 分子 C: 部番も販社も合算
c = d.groupby(["biz","sf","dev"]).agg(C=("use","sum"), nb=("part","nunique"), ...)

# 分母 E: 保有台数。★部番で水増ししないよう月ごとに1回だけ数える
fm = (d.groupby(["biz","dev","ym","dist"])["fleet"].max()      # 部番をまたいで max
        .groupby(["biz","dev","ym"])["fleet"].sum())           # 販社は合算
e  = fm.groupby(["biz","dev"])["fleet"].sum()
```

**`fleet` を `max` で取っている理由**：同じ機種の同じ月に部番が2つあると、
単純に `sum` すると保有台数が2倍に見えて O/E が半分に潰れる。
nb=1 の機種と nb=2 の機種で E が完全一致することを確認済み。

`require_full=True` は「経過月0〜cap を完走した機種だけ比較する」という制約。
若い機種を除外する代わりに、比較の公平性を担保する。

#### 検定（`_peer_compare`）

leave-one-out でピアと比べる。

```python
u["C_peer"] = g["C"].transform("sum") - w["C"]     # 自分を除いた群の合計
u["E_peer"] = g["E"].transform("sum") - w["E"]
u["expected"] = (C_peer / E_peer) * E              # ピアのレートを自分の露出に当てる
u["O_E"]      = C / expected
u["p"]        = 条件付き二項
```

`key` は `["biz","sf","nb"]`（nb層別）。**nbが一致する機種同士だけ比較する。**
nbで割る正規化は実測で成立しなかった（nb=2→1.39倍, nb=3→3.66, nb=4→5.09）。
しかも「交換が多い→改良品番が追加→部番数が増える」という因果の逆流があるので、
nbで割ると異常の証拠を割り算で消してしまう。

#### 2パス（汚染除去）

1パス目で発火した機種を**ピアプールから外して**再計算する。

```python
bad  = (p <= alpha) & (C >= min_count) & (O_E >= min_oe)
flag = 発火した (biz,sf,dev) に True
u2   = _peer_compare(u0, key, min_peers, exclude=flag)
# 除外するとピアが min_peers を割る群は1パス目の結果を使う（下の keep）
keep = u に居て u2 に居ない行
u    = concat([u[keep], u2])
```

同群に複数の異常機種があると基準が押し上げられて互いに打ち消し合う。
検証では正常機種の O/E が 0.73 → 1.05〜1.10 に是正された。
**副次効果として、「新常態受容」した既知高水準の機種が自動的にピアから外れる。**

#### 発火条件と注目度

```
発火 = (O/E ≥ min_oe) かつ (p ≤ alpha) かつ (C ≥ min_count)
注目度 = min(1.0 + 2.0 × (O/E − min_oe) / (2×min_oe), 3.0)
```

**主レバーは `min_oe`。`alpha` はほぼ効かない。** 件数Cが数百になると p値が桁で
吹き飛ぶ（O/E=1.27 で p=6e-4、O/E=2.48 で p=1e-58。この間に55桁の差）。
実測でも min_oe≥1.3 の領域では alpha を50倍絞っても発火件数が1件も変わらなかった。
注目度も p 値でなく O/E ベースにしてある（p は桁が飛びすぎて並び順にならない）。

`alpha` は件数の少ない群（C が10〜30）で偶然 O/E が2倍になるのを落とすガード。

**時間特性**：経過月0〜cap の累積なので月次でほとんど動かない。
だから `SUPPRESS_MONTHS["信号B"]=12`。短くすると同じ機種が毎月鳴り続ける。

### 5.3 信号C — `signal_c_dist.run_signal_c`

「特定の国で、その部品が突然増えたか」。

#### 前処理（`prepare_dist_panel`）

ALL行を除外し、系列ごとに月次0補完する。

```python
# 各 (biz,dev,part,dist) の初出月〜最終月を埋める
g2["use"]   = g2["use"].fillna(0.0)
g2["fleet"] = g2["fleet"].ffill()
```

**補完はその系列自身の最終月まで。** 販社Dの行が202412で終わっていれば、
そこで系列も終わる。だから遅れている販社に偽ゼロは入らない。

#### 検定（`_rolling_test`）

各月 t について、直近 `base_len` ヶ月をベースラインにする。

```python
a = max(0, t - base_len)                    # 窓の左端
if t - a < min_base_months: continue        # 左側打ち切りガード
C = 窓内の use 合計
E = 窓内の fleet 合計
if E <= 0 or C < min_base_count: continue   # 薄すぎる窓は判定しない

rate = C / E
exp  = rate * fleet[t]                      # この月の期待件数
O_E  = use[t] / exp

if use[t] < min_count or use[t] <= exp: continue   # ★高速化: 上振れだけ検定
p = binom_sf(use[t], use[t] + C, fleet[t] / (fleet[t] + E))
alert = (p <= alpha)
```

`use[t] <= exp` で切っているので、**下振れの月は p が NaN のまま残る**。
これは意図的な高速化。注目度も NaN → 0 になる。

```
注目度 = min(log(p) / log(alpha), 3.0)
```

信号Bと違い p ベース。件数が小さいので p の桁が飛びすぎず、物差しとして機能する。
この非対称は意図的。

**既知の性質**：緩やかな上昇トレンドがあるとローリングベースラインが遅れて
追随するため、上振れした月で鳴る。バグではない。緩やかな上昇は閾値・CUSUMの
担当なので、運用では「単月か継続か」を目視で切り分ける。

### 5.4 共通の統計：条件付き二項検定

信号B・信号Cとも `cusum_monitor.binom_sf` を使う。同じ考え方。

> 2つのポアソンレートが等しいという帰無仮説のもとで、
> 合計件数 n = C_focal + C_peer を固定すると、
> 焦点側の件数は X ~ Binomial(n, E_focal / (E_focal + E_peer)) に従う。
> p = P(X ≥ C_focal)

**なぜ素朴なポアソン検定でないか。** ベースラインの λ を「既知の真値」として
扱うと、12ヶ月程度の短い窓では λ を過小推定し、誤報率が理論値の数十倍になる。
条件付き二項は推定の不確実性を構造的に吸収し、ベースラインが薄いほど自動的に
保守側に開く。決して素朴版より鳴りやすくならない。

## 6. 台帳の解決 — `LedgerView`

### 6.1 初期化

```python
led = ledger[ledger["判定年月"] <= T]                 # 未来の記録は無視
self.machine_end = {(biz,dev)}                        # 機種終了
self.last = {(biz,dev,part): その部品の全記録（判定年月順）}
```

### 6.2 `status()` の判定順序

```
機種終了か？                     → 終了機種（永久に出さない）
  ↓ no
記録が無い？                     → 未記録（そのまま出す）
  ↓ ある
監視終了が1件でもあるか？        → 終了単位（永久に出さない）
  ↓ no
最後の記録が「保留」か？         → 要確認保留（★抑制を無視して毎月出す）
  ↓ no
detector=None なら              → 監視中（ここで打ち切り）
  ↓ 検出器を指定
その検出器を含む記録を抽出
  かつ 判定年月 ≤ event_ym       ← ★遅延対応で追加
  ↓ 無い
                                 → 監視中（抑制なし）
  ↓ ある（最後の1件を採用）
until = 再評価年月 or 判定年月 + SUPPRESS_MONTHS[検出器]
suppressed = (event_ym < until)
```

**3つの階層がある。**

| 階層 | 対象 | 例 |
|---|---|---|
| 部品単位・永久 | 全検出器 | 監視終了 / 機種終了 |
| 部品単位・毎月出す | 全検出器 | 保留 |
| **検出器単位・期限つき** | その検出器のみ | 対策中 / ノイズ / 新常態受容 |

**検出器ごとに独立なのが設計の中核。** 信号Bを12ヶ月抑制しても、その間に販社で
急増が起きれば信号Cは出る。これを部品単位にすると12ヶ月間すべての検出器が
盲目になる（設計途中で踏んだ穴）。

`_covers()` は台帳の検出器欄を `/` で分割して照合する。
**空欄は「全検出器」とみなす**ので、記入漏れは抑制を広げてしまう。

### 6.3 `event_ym`（遅延対応で追加）

抑制は「run月Tが窓内か」でなく **「発火月が窓内か」** で判定する。

```
判定年月 ≤ 発火月 < 再評価年月  →  抑制
```

販社の報告遅れで過去月が後から発火するようになったため。
`event_ym=T` を渡せば従来と完全に同じ結果になる（後方互換）。

**この設計が、台帳の `判定年月` を「最も古い発火月」にする理由でもある。**
run月に書き換えると `判定年月 > 発火月` になり、次回runで抑制が効かず二重に出る
（実測で再現済み）。

## 7. 統合 — `merge_candidates`

```python
# ① 台帳による抑制（信号B/Cはここで初めて適用）
keep = [not status(..., event_ym=r.判定年月)["suppressed"] or carry for r in c]

# ② 1部品1行に畳む
g = c.groupby(["事業コード","開発コード","部番"]).agg(
      検出器   = "/".join(sorted(set, key=DETECTORS.index)),   # 表示順を固定
      最大スコア = max(生スコア),
      判定年月  = min(判定年月),        # ★最も古い発火月
      対象月内訳 = 全発火月,
      ...)

# ③ 統合注目度
統合注目度 = 最大スコア + 0.5 × (検出器数 − 1)
```

**複数検出器の同時発火は真陽性率が高いはずなので加点する。** 各検出器の生スコアは
3.0 で頭打ちなので、加点がなければ「全部3.0」で並び順が消えてしまう。

閾値は `candidates_threshold` の中でも抑制を見ているので二重に効くが、
結果は同じなので害はない。

**信号Bは実部番に展開してから統合する**（`candidates_signal_b`）。
信号Bの単位は機種×SFなので、そのままだと `[SF]SF-100` のような擬似部番になり、
台帳に記録しても信号B行だけ消えて閾値行が残る。実績のある実部番に展開してキーを揃える。

## 8. 遅延レイヤー

### 8.1 なぜ検出器で扱いが違うか

| 検出器 | 遅れの影響 | 対処 |
|---|---|---|
| 閾値 | 分母は完全・分子だけ欠ける → 率が**過小**。見逃し方向のみ | そのまま。欠測販社を `completeness` に注記 |
| 信号B | 機種ごとに販社構成が違うので機種間比較が**不公平**に歪む | `hz_global` で打ち切り。遅い検出器なので実害なし |
| 信号C | 遅れている販社の月が**永久に未検定** | 販社ごとに切る + 再評価窓 |

### 8.2 `reporting_horizon.estimate_horizon`

```
horizon[販社] = その販社の行がある最大の年月 − margin
margin = 0（既定）+ 1（auto_margin: 末尾月が痩せていれば）
```

監視単位が3000件あるので、ある販社がその月に1件も報告しないことは実質ない。
だから「行がある最大の年月」＝受領済み最終月とみなせる。

**margin が送付頻度で変わるのが肝。** 月次一括送付なら最終月は完結しているので0、
毎日／週次なら月の途中で切れるので1。`auto_margin` は末尾月の使用数計が
直前6ヶ月の中央値の `thin_ratio`（既定0.7）未満かで自動判定する。

### 8.3 信号Cへの効き方

```python
Td = min(T, horizon[dist])
g  = g[g["ym"] <= Td]          # ★検定の前に切る
sel = (ym <= Td) & (ym >= shift(T, -(months_back + revisit_months)))
```

**切るのが検定の前**なのが重要。未確定月をローリングベースラインに残すと
レートが下振れし、翌月が鳴りやすくなる。

`revisit_months` は「直近K ヶ月を毎回判定し直す」。**0のままだと遅れている販社の
月は一度も検定されない。** K は販社の最大遅れ月数以上にする。

副作用として、遅れが無くても過去K ヶ月が毎回判定対象になる。初回runでは
「これまで一度も検定していなかった月の答え合わせ」がまとめて出る。
2回目以降は台帳に記録済みの月が抑制で消える。

### 8.4 `USE_HORIZON` はマスタスイッチ

`False` にすると `horizon=None` かつ `revisit_months=0` になり、
遅延対応前と完全に同一挙動になる。回帰確認の土台。

### 8.5 `panel_maturity` — 熟成カーブ

集計パネルは受付月ベースなので、**同じ受付月の値が抽出のたびに増える**
（修理完了→販社送付を経て届くため）。これを測る2経路。

- `maturity_curve()` … 直近k ヶ月のレートが成熟した過去月の何割かを推定。いま使える近似
- `save_snapshot()` / `build_triangle()` … 毎月のカバレッジを貯めて実測。正解だが数ヶ月かかる

`run_month.py` が毎回スナップショットを自動保存している。

## 9. 触ると壊れるところ

実測・検証で決まった値。理由なしに変えない。

| 箇所 | 理由 |
|---|---|
| `B_NB_STRAT = True` | nb正規化が成立しない（1.39/3.66/5.09） |
| `B_TWO_PASS = True` | ピアプール汚染で O/E が0.73に潰れる実測あり |
| `SUPPRESS_MONTHS["信号B"] = 12` | 累積O/Eが月次で動かない。短いと毎月鳴る |
| `build_peer_units` の `fleet` を `max` | `sum` にすると O/E が半分に潰れる |
| 信号Bを実部番に展開してから統合 | キーが揃わず同じ部品が二重に出る |
| 抑制を検出器単位で | 部品単位にすると全検出器が盲目になる |
| `判定年月` = 最も古い発火月 | run月にすると次回runで抑制が効かない |
| 検定は条件付き二項 | 素朴ポアソンだと誤報率が数十倍 |
| horizon で**検定の前に**切る | 後で切るとベースラインが汚れる |

## 12. よくある誤解

**「`TOP_N` を上げれば検知率が上がる」** — 上がらない。検知率を決めるのは
検出器のパラメータ（`B_MIN_OE` / `C_ALPHA` / 閾値）。`TOP_N` が変えるのは
「いつ処理するか」であって「拾えるか」ではない。インボックスに載っているのに
上位N件に入らない（△載るが沈む）と、載りもしない（×未検知）は別問題。

**「`B_ALPHA` を絞れば信号Bが厳しくなる」** — ならない。件数が数百になると
p値が桁で飛ぶので、50倍絞っても発火件数が変わらない実測がある。`B_MIN_OE` を使う。

**「`scan_b.csv` の O/E 分布 = 本番の分布」** — 違う。`tune_b_minoe.scan()` は
1パス（`two_pass=False`）で計算している（2パス目の判定が min_oe/alpha に依存し、
1回のスキャンで全操作点を表せないため）。本番は2パスなので、正常機種の O/E が
1.0へ是正されて分布が上にずれる（実測: 中央 0.95 → 1.01）。
操作点を選んだら `tune_b_minoe.confirm()` で本番の値を確認する。

**「横断比較なら何でも拾える」** — 拾えない。同SF群の全機種で同じ部品が不良なら
差が出ないので沈黙する。全社共通部品の不良は時系列側（CUSUM）でしか拾えない。
**2軸は補完関係で、片方だけでは穴が残る。**

**「累積使用率が正しい値」** — 報告遅れがあるあいだは過小に出ている。
誤報にはならないが、直近の数字を絶対値として信じない。
`完全性_YYYYMM.csv` にどの販社が欠けているかが出ている。
