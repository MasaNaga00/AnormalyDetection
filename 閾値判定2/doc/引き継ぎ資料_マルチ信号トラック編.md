## 1. 方針転換の理由と位置づけ

### 1.1 なぜCUSUM単独をやめたか
過去の検出データを拾おうとすると多数の部品が発火し、triage予算に収まらなかった。
一方、**部品の使用率に閾値を設ける方法なら、ノイズを抑えつつ過去例を拾える**ことが
分かっていた。業務として本番運用を始める必要があったため、確実に動く方を本線にした。

### 1.2 CUSUMを捨てない理由
- 台帳・処置区分・レビューループ・asof再現性は**検出手法に依存しない資産**。そのまま使える。
- CUSUMの過検知は設定の問題（監視範囲60ヶ月上限による累積販売台数の過大評価、
  矩形カーネルの露出定義、ベースライン汚染）で、腰を据えて直す類のもの。
  運用開始の締切と同じ土俵で戦わせるべきではない。
- **閾値運用はCUSUMの前提条件（正解ラベル）を作る作業でもある。**
  半年で数十件のラベルが溜まれば、そのときの再チューニングは今より遥かに精度が出る。

### 1.3 CUSUMはシャドー実行
triageはしない。発火記録だけ残す。半年後に台帳と突き合わせ、
「閾値・信号B・信号Cが拾えず、CUSUMだけが拾っていた件」を数える。
台帳の **`検出器` 列がこの評価の土台**になる。運用コストはほぼゼロ。

---

## 2. 3つの検出器（役割分担）

| | 何を見るか | 拾えるもの | 単位 |
|---|---|---|---|
| **閾値** | 累積使用率の絶対水準 | 最終的に高くなる部品（確実だが遅い） | 機種×部番 |
| **信号B** | 同SF群ピアとの相対水準 | 閾値Xに届かないが同型比で高い部品 | 機種×(biz,SF) → 部番に展開 |
| **信号C** | 販社別の月次急増 | 特定国での突発（累積率では動かない） | 機種×部番×販社 |

### 2.1 なぜ補完的か（重要な理解）
- **CUSUMは自己参照型**（その部品自身の過去との比較）なので、
  **最初から高い水準で平坦に推移する部品は原理的に検知できない**。
  過去に人が見つけていた例はここに集中していた（「フラット高位安定」）。
  信号B/Cは横断比較なので、この構造的盲点を埋める。
- **閾値と信号Cは時間特性が正反対**。累積使用率は分母が積み上がるため単月急増では
  ほぼ動かず、構造的にスパイクを検知できない。信号Cがそこを埋める。
- **信号Bは `threshold_overrides` の自動化**になる。部品ごとのXを人が決める代わりに、
  同SF群から基準を導出する。将来的に上書き作業を減らせる。
- **横断比較は露出（母数）定義の偏りが比の分子分母で相殺されやすい。**
  矩形カーネルの E=0 問題や60ヶ月上限の悩みが効きにくくなる副次効果がある。

### 2.2 共通の限界（運用ガイドに明記すべき）
横断比較は**比較群が汚染されていると効かない**。同SF群の全機種で同じ部品が
不良なら差が出ないので沈黙する。全社共通部品の不良はCUSUM側（時系列の変化点）で
しか拾えない。**2軸は補完関係にあり、片方だけでは穴が残る。**

## 3. 信号B（`signal_b_peer.py`）

### 3.1 設計
監視単位を「機種 × (biz, SF-CODE)」に集約（部番を合算）。機種間で部番が違っても
比較でき、**部品対応表が不要**になる。検定は条件付き二項（`cusum_monitor.binom_sf` を流用）。

```
対象: 機種X の (C_focal, E_focal)
ピア: 同一(biz,SF)の他機種をプールした (C_peer, E_peer)
H0: 両者のレートが等しい → n = C_focal + C_peer を固定して
    X ~ Binomial(n, E_focal/(E_focal+E_peer)), p = P(X >= C_focal)
```

`earlylife_baseline` の階層フォールバックが既に `biz+sf` をピアキーとして使っており、
その有効性は先行機種カーブの推定で実証済み。同じキーを時間軸でなく機種軸に使い回している。

### 3.2 実装上の必須ポイント（触るときの注意）
- **露出の二重計上を回避している。** `build_peer_units` で fleet を**月ごとに1回だけ**
  数える（部番ごとに合計すると保有台数が水増しされ O/E が半分に潰れる）。
  検証: nb=1 と nb=2 の機種で E が完全一致することを確認済み。
- **nb層別がデフォルト**（`nb_strat=True`）。詳細は3.3。
- **2パス**（`two_pass=True`）。1パス目で発火した機種をピアプールから外して再計算。
  同群に複数の異常があると基準が押し上げられ互いに打ち消し合う。
  検証: 正常機種の O/E が 0.73 → 1.05〜1.10 に是正。
  **副次効果として「新常態受容」した既知高水準機種は自動的にピアプールから外れる。**
- **経過月を揃える**（`elapsed_cap`）。発売年次の差がそのまま出るため。
  `require_full=True` で窓を完走した機種のみ比較。

### 3.3 nb（機種×SF内のユニーク部番数）の扱い — 診断結果つき
実データ診断の実測値:

```
ピア2機種以上のSF群: 約167
  幅0（そのまま比較可）  : 82（約49%）
  幅1                    : 31
  幅2以上                : 約54
最頻の部番数: 1が1063件（約73%）, 2が227, 3が100, 4以上59以下
```

**nbで割る正規化は成立しない**（実測）。同群のnb=1機種を基準にした交換率の比:

| nb | 比 | ÷nb（残差） |
|---|---|---|
| 2 | 1.39 | 0.69 |
| 3 | 3.66 | 1.22 |
| 4 | 5.09 | 1.27 |

揃わない。特にnb=2を2で割ると1機種あたり0.69倍＝**本来より3割低く見え、真の異常を沈黙させる**。

さらに nb=3 が3.66、nb=4 が5.09と**期待値を超えている**。解釈は因果の逆流:
> 交換が多い部品 → 設計変更・改良品番の追加 → 部番数が増える

つまり **nbは設計属性であると同時に不具合の結果でもある**。nbで正規化する行為は
異常の証拠を割り算で消すことになる。

**→ 結論: nbが一致する機種同士だけを比較する（nb層別）。** 幅0の82群が対象、
幅≥1の群も nb ごとに割れて一部が救われる。

### 3.4 副産物: 部番数そのものが検知信号
`rank_part_count_outliers()` を実装済み。「同群のピアより部番数が多い」は
件数とは独立した異常サイン。設計変更という人間の判断の痕跡なのでノイズが乗らない。
**未評価。実データで一度眺める価値あり。**

### 3.5 **操作点は alpha でなく効果量 min_oe で決める（重要な発見）**

信号Bの発火条件は `O/E >= min_oe かつ p <= alpha かつ C >= min_count`。
**主レバーは `min_oe`（B_MIN_OE、既定1.5）。alpha はほぼ効かない。**

理由（合成データでの実測。実データでも構造は同じ）:

```
dev  sf      C    O_E     p
M08 SF-100 250  1.265  6.5e-04   ← 実務的には無意味だが alpha=0.005 を通過
M06 SF-102 490  2.481  1.3e-58   ← 真の異常
M02 SF-101 691  4.246  1.1e-169  ← 真の異常
```

- **件数Cが数百になるとp値が桁で吹き飛ぶ。** O/E=1.27 と 2.48 の間に55桁の差。
  この間のどこに alpha を置くかは実質的に意味を持たない。
- Cが群ごとに違うので、**同じalphaでも群によって効き方が変わる**。
- 実データでは機種が正当な理由（設計世代・市場構成・使用環境）で本当に違う＝
  **帰無仮説が最初から成り立っておらず、過分散のぶんp値はさらに小さく出る**。

スイープ実測でも、min_oe>=1.3 の領域では alpha を 0.05→0.001 と**50倍絞っても
発火件数が1件も変わらなかった**。一方 min_oe は 1.2/1.3/2.5 で 3/2/1件と素直に効く。

**注目度もO/Eベースに変更済み**（旧: log(p)/log(alpha)）。p値は桁が飛びすぎて
並び順の物差しにならない。min_oe で1.0、その3倍で3.0 になる線形スケール。

`B_ALPHA` は**補助レバー**として残す。件数の少ない群（C が10〜30程度）では
偶然でO/Eが2倍になり得るので、そこのガードとして機能する。0.005 のままでよい。

### 3.6 信号Bの件数は「月次」でなく「立ち上げ初回」で考える
発火すると12ヶ月抑制されるので、月次の定常件数ではなく**初回の総件数**が制約になる。
初回に多く出ても、翌月以降は新機種が窓（elapsed_cap）を完走した分の細い流入だけ。
→ **初回だけ min_oe を高めにして上澄みから着手し、落ち着いてから下げる**段階運用が現実的。

### 3.7 **件数の下限（誤発火率でなく順位の問題）**

実データで「累積10個以下の部品同士が比較されて検知される」症状が出た。
調べると、**誤発火率そのものは低いのに O/E の値が異常に大きくなる**のが原因だった。

全機種が同じ真のレート（＝異常なし）でのシミュレーション:

| 1機種あたり平均件数 | 誤発火率 | **ノイズだけで出るO/E最大** |
|---|---|---|
| 3件 | 0.20% | **6.67** |
| 10件 | 0.30% | **2.91** |
| 50件 | 0.05% | 1.51 |
| 200件 | 0.00% | 1.35 |

変動係数が $1/\sqrt{\mu}$ なので、薄い単位では O/E が構造的に大きく振れる。
注目度はO/Eベースなので、**10件の部品がノイズで出したO/E=2.9が、500件の部品の
真のO/E=2.5より上位に来る**。検知の問題ではなく**順位の問題**。

対処として**対象側とピア側の両方**に件数下限を置いた（ピア側が薄いと期待値の推定が
不安定になり、同じくO/Eが暴れるため）。

| 下限 | 判定対象率 | ノイズ由来のO/E最大 |
|---|---|---|
| 3（旧既定） | 89.8% | **5.33** |
| **20** | 44.3% | **2.05** |
| 50 | 23.8% | 1.51 |

→ `B_MIN_COUNT = 20`, `B_MIN_PEER_COUNT = 20`（旧: min_count=3, ピア側は制限なし）。
代償として判定対象が半減する。薄い部品の突発は信号Cの担当領域なので役割分担としては整合。

### 3.8 部番展開のシェア絞り込み（`B_EXPAND_MIN_SHARE`）
信号Bの判定単位は「機種×SF」だが、台帳のキーは部番なので展開が要る。
旧実装は「実績1件以上」で展開していたため、**SFが C=500 で発火すると、その中の
累積1件の部番までレビューに並んだ**（件数下限はSF単位の合計にしか効かない）。

実データの内訳を確認すると、**1%未満の端数が4件、7:3の分担が1組**と二極化していた。
その間にある 0.1 を閾値にすれば両方を正しく扱える。

- 10%未満の部番は展開しない。落とした分は指標欄に `＋他2部番(5件)` と併記
- どのSFでも最低1部番は必ず残す（全部が閾値未満なら最大のものを採用）

### 3.9 低い側は拾わない（確認済み）
p値が上側裾 $P(X \ge C_{focal})$ だけを見ており、かつ `min_oe >= 1.5` があるので、
ピアより低い機種は二重に弾かれる。実測でも低い側32件のp値は最小0.574（中央0.959）。

`信号B詳細_YYYYMM.csv` には O/E<1 の行も残るが `alert_peer=False` でインボックスには
載らない。レビュー時に「同群の他機種がどうなっているか」を見るために残している。

## 4. 信号C（`signal_c_dist.py`）

### 4.1 設計
- 監視単位は**機種×部番×販社**（合算しない）。1国だけ3倍でも他4国が平常なら合算では埋もれる。
- ベースラインは**直近Nヶ月のローリング窓**（既存 spike_test は経過月4〜15の固定窓）。
  「過去1年の交換率と比べて突然増えた」という定義に合わせた。
- 検定は同じ条件付き二項。

### 4.2 データ上の必須知識（ALL行問題）
元データの販社列には **ALL（全販社合計）と個別販社A〜E が両方入っている**。
修理が1件でも入る前の月は行が生成されないため、全販社の販売台数総計を
毎月取れるようにする目的でALL行がある。

**`state_logic.py` も `state_logic_cusum.py` も販社でフィルタしていない**
（`dist` はソートとゼロ埋めのグループキーのみ）。ALL行と個別行を同じパネルに
入れると use も fleet も正確に2倍になり、CUSUM増分が2倍＝**hを半分にしたのと同じ**になる。
→ 本件はユーザ側で既に対処済み（ALLとそれ以外でデータを分けて閾値調整していた）。
**新チャットでも必ず `panel[panel.販社=="ALL"]` と `!= "ALL"` に分けて使うこと。**

- 本線・信号B → **ALL行のみ**（1機種×部番×月あたり1行なので合算が実質no-opになる）
- 信号C → **販社別行のみ**

販社別行は左側打ち切り（初回修理まで行が無い）があるため、
`min_base_months` / `min_base_count` でガードしている。

### 4.3 既知の性質（バグではない）
**緩やかな上昇トレンドがあると、ローリングベースラインが遅れて追随するため
上振れした月で鳴りやすい。** 合成テストで再現（判定500行で2件＝alpha=0.005の設計値どおり）。
緩やかな上昇は閾値／CUSUMの担当なので、運用では「単月か継続かを目視で切り分ける」で足りる。

### 4.4 **実データ投入前の必須作業（最優先の未実施項目）**
3086単位 × 5販社 ≈ **15,000系列**を毎月検定する。`alpha=0.005` のままだと
**月数十件**出る可能性があり、top_n=15 を単独で食い潰す。

```python
import pandas as pd, signal_c_dist as sc, run_month as rm
raw = pd.read_csv("panel.csv", encoding="utf-8-sig")
r = sc.run_signal_c(raw[raw.販社 != "ALL"], rm.COLS, months_back=24, alpha=0.005)
print(r[r.alert_dist].groupby("ym").size())   # 月あたり何件だったか
```

月5件程度に収まるまで `c_alpha` を絞る。同時に**過去に人が見つけた急増例が
この中に出るか**も確認できる（一石二鳥）。

### 4.5 **p値でなく効果量で切る（今回の最大の変更）**

実データで回したところ、**累積件数の多い系列が、グラフで見て大した変動でないのに
鳴る**という症状が出た。原因は信号Bと同じ構造で、p値は件数が増えるほど小さくなる。

alpha=0.005 で発火する最小の倍率を、ベースライン規模別に計算した実測:

| 月平均 | 発火する当月件数 | そのO/E | 増加分 |
|---|---|---|---|
| 0.5件 | 5件 | **10.0倍** | +4 |
| 2件 | 8件 | 4.0倍 | +6 |
| 10件 | 21件 | 2.1倍 | +11 |
| 50件 | 71件 | **1.42倍** | +21 |

**月50件の系列は1.42倍で鳴る。** 一方、探したい「ほぼゼロ→突然多数」は10倍を要求される。
完全に逆になっていた。→ `C_MIN_OE`（既定3.0）を主レバーに追加。注目度もO/Eベースへ。

### 4.6 ゼロベースラインの盲点（発見・修正済み）
過去の実例は「毎月ほぼ0件→突然多数」型だったが、**これが構造的に検知できなかった**。

```python
rate = C / E          # C=0 なら rate=0
exp = rate * fleet[t] # → exp=0
if exp <= 0: continue # ← ここで必ず抜ける
```

条件付き二項は C=0 でも定義できる（n=当月件数、p=π^x）。詰まるのはO/Eの分母だけなので、
**そこにだけ 0.5 の下駄**を履かせた（Jeffreys相当）。p値には実測のCをそのまま使う。

あわせて `C_MIN_BASE_COUNT` の既定を **3.0 → 0.0（制限なし）** に変更。
条件付き二項は薄い窓で自動的に保守側に開くので、件数で足切りする必要が本来ない。
**3 のままだと最も拾いたいパターンを判定前に消していた。**

### 4.7 もともと振れの大きい系列（`C_EXCEED_HIST`）
`min_oe=3.0` は純粋なポアソン変動を完全に止める（月10件以上の系列で誤発火率0%）。
それでも鳴るなら本当に3倍振れている＝まとめ発注・季節性など構造的なもの。

対処として **自己履歴による下限**を用意した。ベースライン窓でその系列が見せた
最大の振れ幅 × `exceed_hist` を超えないと発火しない。

| exceed_hist | 平常時の発火 | 本物(8倍)の検知 |
|---|---|---|
| 0.0（無効） | 7.40% | 98.8% |
| **1.2** | **4.74%** | **84.5%** |
| 1.5 | 3.08% | 57.0% |

振れの小さい通常部品には影響しない（4倍の本物は100%検知のまま）。
既定は0.0（無効）。症状が出たら1.2から試す。

消耗品など性質上つねに出入りが多い部品は、統計に頼らず `C_EXCLUDE` で名指しで外す。

> **試して却下**: 過分散補正（統計的には筋が良い）も実装して測ったが、
> **本物の検知率が 98.8% → 17%** と壊滅した。件数の少ない月で正規近似が
> 効きすぎるのが原因。採用していない。

### 4.8 分母（販売台数）は要るのか — 検証済み
「件数だけ見ればよいのでは」という問いに対する答え。**販売台数が横ばいなら両者は
数学的に完全に同一**（π = F/(F+12F) = 1/13 で F が約分される）。差が出るのは成長期だけ。

レート一定（＝異常なし）で台数が伸びている場合:

| 月次成長率 | 当月/平均 | 件数のみ p | 率ベース p |
|---|---|---|---|
| 0% | 1.00 | 0.53 | 0.53 |
| 6% | 1.43 | 0.025 | 0.54 |
| 10% | 1.76 | **5.3e-05**（誤発火） | 0.51 |

**件数のみだと成長期の新機種で系統的に誤報が出る。** 分母は立ち上がり期の保険として
機能しているので外さない。実データでの効き具合は `diag_fleet_growth.py` で測れる。

## 5. 統合インボックスと台帳（`unified_inbox.py`）

### 5.1 台帳は案1（CUSUM版スキーマ）に統一
`state_logic.py` の `再アラート条件タイプ + 条件パラメータY` ではなく、
`state_logic_cusum.py` の `処置区分 + 上書き列` に寄せた。8処置区分は
検出器に依存しない汎用的な語彙で、リセット・再評価・終了の意味論がそのまま使えるため。

**追加した3列:**

| 列 | 用途 |
|---|---|
| **検出器** | 閾値/信号B/信号C/CUSUM（複数なら"/"）。**半年後の評価の要** |
| **上書き閾値** | 新常態受容で閾値X(%)を引き上げる値 |
| **対象販社** | 信号Cで特定販社の話のとき |

テンプレート: `台帳テンプレート_統合版.xlsx`

### 5.2 抑制モデル（設計の中核）
CUSUMだけはSを積むためセグメント分割が要るが、**閾値・信号B・信号Cは状態を持たない**
ので、台帳の役割は3つに縮退する:

1. **終了**（監視終了/機種終了）… 部品単位・恒久
2. **抑制**（再評価年月まで消し込み）… **検出器ごとに独立**
3. **基準上書き**（新常態受容 → 上書き閾値）

**「保留」は率に関係なく毎月出続ける**（放置の検知漏れ防止）。部品単位で全検出器に効く。

### 5.3 検出器ごとの既定抑制期間（`suppress_months`）
台帳の再評価年月が**空欄なら** `判定年月 + 下記月数` まで抑制。記入があればそちらが優先。

```python
"suppress_months": {"閾値": 6, "信号B": 12, "信号C": 3, "CUSUM": 1}
```

**信号Bが12ヶ月なのは経過月0〜cap の累積O/Eが月次でほぼ動かないため。**
短くすると同じ機種が毎月鳴り続ける。

**抑制が検出器ごとに独立していることが重要。** 信号Bを12ヶ月抑制しても、
その間に販社で急増が起きれば信号Cは出る。これを部品単位にすると
12ヶ月間すべての検出器が盲目になり危険（設計途中で踏んだ穴）。

検証済み（`test_suppress.py`）:
```
記録から 2ヶ月 → 閾値のみ（信号Bは黙る）
記録から11ヶ月 → 閾値のみ
記録から12ヶ月 → 閾値/信号B（復帰）
保留を0/3/20ヶ月前に記録 → いずれも毎月表示
信号B抑制中のM1 → 閾値/信号C は生きている
```

### 5.4 信号Bは実部番に展開してから統合する
設計途中で踏んだ穴: 信号Bの単位が `[SF]SF-100` という擬似部番だと、
台帳に記録しても信号B行だけ消えて**閾値行が残り、同じ部品を2回レビューすることになる**。
→ `candidates_signal_b` で発火した(機種,SF)を**実績のある実部番に展開**してから統合。
キーが揃い、1部品1行にまとまる。

### 5.5 統合注目度
```
統合注目度 = max(各検出器の生スコア) + multi_bonus × (検出器数 - 1)
  閾値   : 観測率 / 当月閾値（上限3.0）
  信号B  : log(p)/log(alpha)（上限3.0）
  信号C  : 同上
  multi_bonus = 0.5
```
**複数検出器の同時発火は真陽性率が高いはずなので加点する。**

### 5.6 実運用での効き方（合成データで確認した重要な性質）
閾値を低めに設定して5機種すべてが発火する状況（＝実データの過検知状態と同じ形）を作ると、
信号Bを重ねることで**真に高い機種だけが加点されて上位に分離**し、正常機種は
閾値単独のまま下に沈んだ。**信号Bは検知を増やすだけでなく、閾値の過検知を
並び替えで整理する方向にも効く。** 閾値を緩めずに実用件数へ落とす道筋になる。

## 6.5 操作点を決めるツール（実データ投入前に使う）

### `tune_c_alpha.py` — 信号C
p値の計算が重いので**1回だけスキャンして `scan_c.csv` に保存**し、
alpha/min_count のスイープはフィルタで行う設計。

```bash
python tune_c_alpha.py panel.csv [labels.csv]
```
```python
import pandas as pd, tune_c_alpha as t
scan = pd.read_csv("scan_c.csv", encoding="utf-8-sig")
t.step2_sweep(scan, alphas=[1e-3, 5e-4], min_counts=[3, 5])
t.step2b_monthly(scan, alpha=0.001, min_count=3)     # 月別推移。塊がないか
t.missed_labels(scan, "labels.csv", 0.001, 3)        # 取りこぼしを理由つきで
```

**見るべきは `単位月最大`**（機種×部番に畳んだ件数の最大月）。平均が3件でも
最大20件の月があればその月は破綻する。同じ部品で複数販社が同時に鳴るので、
`月平均`（販社別の行数）より実態に近い。

### `tune_b_minoe.py` — 信号B
```bash
python tune_b_minoe.py panel.csv [labels.csv]
```
```python
import pandas as pd, tune_b_minoe as tb
s = pd.read_csv("scan_b.csv", encoding="utf-8-sig")
tb.top_list(s, min_oe=1.5, alpha=0.005)   # 実際に何が出るかを目視
```

**まず `O/E の分布`（中央/P90/P95）を見る。** 合成データはピュアなポアソンなので
P95=1.16 に収まったが、**実データは過分散があるのでもっと広がる**はず。
P95が1.4なら min_oe=1.5 で5%が鳴る計算になる。分布を見てから決める。

**`top_list` で中身を目視するのが一番効く。** 「これは異常」「これは機種特性」と
人が判断できる境界がO/Eのどこにあるかは、実データなら見れば分かる。統計量より信頼できる。

### `inject_power.py` — **ラベルが無くても検出力が測れる**
品目によっては過去の実例（ラベル）が無い。その場合でも、実データの系列に人工的な
異常を注入すれば検出力カーブが描ける。実データの分布・露出・ノイズをそのまま使うので
合成パネルより実態に近い。

```python
import inject_power as ip
ip.sweep_b("panel.csv", "min_oe", [1.2, 1.5, 2.0, 2.5])
ip.sweep_c("panel.csv", "min_count", [2, 3, 5, 8], min_oe=3.0)
```
```
 min_oe  1.5倍    2倍    3倍  5倍  初回発火数  判定対象数
    1.2 0.800 1.000 1.000 1.0      3      53
    1.5 0.333 0.900 1.000 1.0      2      53
    2.0 0.033 0.367 0.967 1.0      2      53
```

**左側＝拾えるか / 右側＝見きれるか。両立する行を選ぶ。**
`settings.py` は書き換えず、引数で上書きして試せる。

**倍率の意味**: 信号Cは「直近12ヶ月の月平均の何倍の件数がその月に入ったか」。
信号Bは「同SF群の他機種と比べて何倍の交換率か」。
台数が伸びているとO/Eは倍率よりやや小さく出る（倍率＝現場から見た見え方、
O/E＝検出器の内部値）。

**どの変数が効くかはデータで変わる。** 合成データでは平常月平均が1.3件しかなく、
`min_count=3` が先に効いていて `min_oe` を振っても動かなかった。
**振って動かなければ、それは効いていない**ので次の変数に移る。

優先して振る順序:
- 信号B: `min_oe` → `min_count` → `elapsed_cap` → `min_peers`
- 信号C: `min_oe` → `min_count` → `alpha` → `exceed_hist`

### `diag_b_row.py` / `diag_fleet_growth.py` — 症状が出たときの診断

`diag_b_row` は4つの発火条件を ○/× で1つずつ出し、そのSFに紐づく部番の内訳も表示する。
「なぜこれが出たのか」を辿る最短経路。

### `signal_c_dist.inspect()` — 特定部番の月次トレース（Jupyter用）
```python
sd.inspect(raw, st.COLS, dev="M01", part="100-0", dist="C", months=24)
```
```

  C 202405    4 1540 1.40 2.85          O/E2.8<3.0

```
**`判定` 列に沈黙の理由が出る**ので、どのパラメータを緩めれば拾えるかが直接読める。

### `check_rank.py` — 過去例が上位N件に入るか（**本番可否の最終判定**）
```bash
python check_rank.py panel.csv labels.csv
```
各ラベルについて報告月の lookback ヶ月前〜報告月を `asof_ym` で再現し、
「インボックスに載った最初の月」と「上位N件に入った最初の月」を出す。

| 判定 | 意味 | 対処 |
|---|---|---|
| **○** | 上位N件に入った | — |
| **△載るが沈む** | 検知はできているが順位で負けた | **N引き上げ、または別枠** |
| **×未検知** | インボックスにすら載らない | 検出器のパラメータか構造的な穴 |

**△と×を混同しないこと。** 前セッションの早期段階ラベルと同じ切り分けで、
△なら `top_n` を上げれば解決するが、×は検出器側の問題。
`最良順位` 列に必要なNが直接出るので、分布を見てN引き上げか別枠かを判断する。

実装上の注意（手で書き直す場合）:
- **台帳は必ず空を渡す**。実台帳だと過去記録による抑制で「未検知」に見える。
- **ラベルごとでなく月ごとにループする**。信号Bは毎回ピア比較を計算し直すので、
  ラベル20件×6ヶ月=120回を、重複を消して月単位にすると大幅に減る。

## 9. 引き継ぎ上の注意

- **`仕込み一覧.csv` は答え合わせ用。** シミュレーションを体感する前に開かない。
- **CUSUM関連の既存課題は消えていない。** スパイク確認→ドリフト再点灯（issue 4.1）、
  早期段階ラベルのtop-N沈み（5章）などは、CUSUMを本採用する判断が出た時点で復活する。
- **信号B/Cは `cusum_monitor.binom_sf` に依存している。** cusum_monitor を差し替える際は
  この関数のシグネチャを壊さないこと。
- **`reset_after_alarm=False` 固定**（CUSUM側）は変更しない。
- **設定を分散させない。** `settings.py` に集約済み。ツールを追加するときも
  パラメータはここに置き、import して使うこと（列名の食い違い事故を防ぐ）。
- **信号Bの操作点を alpha で調整しようとしない**（3.5）。効かない。min_oe を使う。
- **信号Cも同じ**（4.5）。p値は件数が多い系列ほど小さくなるので、`C_MIN_OE` で切る。
- **`C_MIN_BASE_COUNT` を上げない**（4.6）。上げると「ほぼゼロ→突然多数」が
  判定前に消える。既定0のままにする。
- **件数下限は誤発火率のためではない**（3.7）。薄い単位がノイズで大きなO/Eを出して
  上位を占拠するのを防ぐため。「誤発火率は低いから下限は不要」という判断は誤り。
- **過分散補正は試して却下済み**（4.7）。再提案されたら検知率17%の実測を確認すること。
