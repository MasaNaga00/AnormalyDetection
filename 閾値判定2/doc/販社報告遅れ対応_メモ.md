# 販社の報告遅れ対応（マルチ信号トラック）

## 1. 何が問題だったか

販社ごとに修理データの送付頻度が違う（毎日／週次／月次）ため、パネルの
最新月は販社ごとに揃っていない。3月上旬に集計すると、月次送付の販社は
12月分までしか入っていない、ということが起こる。

**最も深刻なのは信号C。** `run_signal_c` は既定で基準月Tの1ヶ月だけを判定する
（`months_back=0`）。遅れている販社はその月の行が存在しないので判定対象にすら
入らず、翌月のrunでもまたTしか見ない。したがって**その販社の12月・1月は
永久に一度も検定されない**。値がズレるのではなく、月が丸ごと落ちる。

副次的な問題:

| 検出器 | 影響 | 対処 |
|---|---|---|
| 信号C | 遅れ月が永久に未検定。未確定月がベースラインを下振れさせ翌月に誤報 | horizon で切る + 再評価窓 |
| 信号B | 分母だけ完全で分子が欠ける。機種ごとに販社構成が違うので累積O/Eが**不公平に**歪む | 全販社が揃う月で打ち切る |
| 閾値 | 累積使用率が過小。**見逃し方向のみ**で誤報にはならず、翌月自動是正 | そのまま。欠測販社を注記 |

## 2. horizon（完全と見なせる最終年月）

外部の受領管理表があるならそれが正解（`HORIZON_FIXED`）。無くてもパネルだけから
決められる。監視単位が3086件あるので、ある販社がその月に1件も報告しないことは
実質起こらない。よって「その販社の行がある最大の年月」＝受領済み最終月。

**margin（末尾から落とす月数）は送付頻度で変わる。**

- 月次一括送付 … 最終月は**完結している** → margin 0
- 毎日／週次送付 … 実行日が月中なら最終月は途中で切れている → margin 1

これを自動判定するのが `HORIZON_AUTO_MARGIN`。最終月の使用数計が直前6ヶ月の
中央値の 0.7 未満なら「まだ途中」と見なして margin を +1 する。

margin を多く取る側に外すのは安全。落とした月は次回の再評価窓で拾い直される。
逆に未確定月を入れるとベースラインが下振れして誤報になる。**迷ったら多めに。**

## 3. 再評価窓（`C_REVISIT_MONTHS`）

信号Cが毎回さかのぼって再判定する月数。**販社の最大遅れ月数以上**にする。
足りないと月が永久に未検定になる。既定6。

`reporting_horizon.report(...)` の `遅れ月数` の最大値を見て決める。窓に収まらない
販社は `判定=再評価窓不足` と出る（`check_revisit` でも取れる）。

再判定した月が毎回インボックスに出てこないよう、**抑制は run月Tでなく発火月で
判定する**ように `LedgerView.status` を変更した。台帳に書く判定年月は
**最も古い発火月**にする（run月にすると次回runで「判定年月 > 発火月」となり
抑制が効かず二重に出る）。

## 4. 変更ファイル

| ファイル | 変更 |
|---|---|
| `reporting_horizon.py` | **新規**。horizon推定・受領状況レポート・欠測販社注記 |
| `signal_c_dist.py` | `run_signal_c` に `horizon` / `revisit_months` を追加。販社ごとに系列を切ってから検定 |
| `unified_inbox.py` | `status(event_ym=)`／`candidates_signal_c` の複数月対応／信号Bの打ち切り／CONFIG追加 |
| `settings.py` | セクション4.5を追加 |
| `verify_lag.py` | **新規**。検証スクリプト |

**既定は完全な後方互換。** `horizon=None, revisit_months=0` および
`use_horizon=False` なら従来と差0（`verify_lag.py` の1項目目で確認済み）。
`settings.py` では `USE_HORIZON=True` にしてある。

## 5. 実データでまずやること

```python
import pandas as pd, reporting_horizon as rh, settings as st
raw = pd.read_csv("panel.csv", encoding="utf-8-sig")
dist = raw[raw[st.COLS["dist"]] != st.ALL_TOKEN]

print(rh.lag_matrix(dist, st.COLS, months=15).to_string())   # まず目で見る
print(rh.report(dist, st.COLS, revisit_months=st.C_REVISIT_MONTHS).to_string(index=False))
```

見るところ:

1. `痩せ比` と `採用margin` が送付頻度の実態と合っているか。合わなければ
   `HORIZON_MARGIN_OVERRIDES` で手当てする。**スパイクが起きた月は痩せ比が
   1を超えるので自動判定が margin 0 に倒れる**（保守側でないが、その月は
   完結しているはずなので実害はない）。
2. `遅れ月数` の最大値。これが `C_REVISIT_MONTHS` の下限。
3. `判定` に `再評価窓不足` がないこと。

その後 `run_month.py` を回すと、初回は過去数ヶ月分の信号Cがまとめて出る。
これは「今まで一度も検定していなかった月の答え合わせ」なので、件数が膨らんでも
慌てない（立ち上げ初月の積み残しと同じ性質）。

## 6. 残っている検討事項

- **run_month.py への配線**：`build_unified_inbox` の戻り値に `horizon_report` と
  `completeness` が増えた。`受領状況_YYYYMM.csv` / `完全性_YYYYMM.csv` として
  出力に加えるのが自然。まだ入れていない。
- **日付列の意味の確認**：`年月` が「修理日」なら遅延、「受領日／取込日」なら
  月次一括送付の販社は**1ヶ月分が1点に潰れた偽スパイク**になる。この場合は
  horizon より先にデータ側の是正が必要。信号Cは確実に鳴る。
- **`C_ALPHA` の実測は再評価窓を入れた後で**。判定行数が窓の分だけ増えるので、
  遅延対応前の実測値では件数が合わない。
- **閾値検出器は未対応のまま**（意図的）。見逃し方向にしか効かないので急がないが、
  「D社が3ヶ月欠けた状態の率」であることをレビュー時に見えるようにする価値はある。
  `completeness` がその材料。
